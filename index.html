Faster than assistant-ui, where your users feel it.

Both apps were measured on the same machine, with the same thread and the same streamed reply. Here is what the difference means for the people using them.

To open a 1,000-message thread, assistant-ui builds a React component and its DOM nodes for every message, including the hundreds nobody can see. Ours lays out only the rows on screen; the rest stay as plain data until you scroll to them. On the same thread it opens 16× faster, and the cost doesn’t grow with history: the demo below opens ten thousand messages in your browser. Your users land in the conversation instead of waiting for it.

As tokens pour in, assistant-ui pushes each update through React and the browser’s page layout, and its longest freeze was long enough to feel. Ours takes the stream in small batches and steps aside after each one, so scrolling, typing and the Stop button always get their turn, and a burst of data becomes one screen update instead of dozens. Its longest pause is 23× shorter, too brief to see. Your users can read, scroll and interrupt mid-answer without the app fighting them.

At the end of the same stream, the assistant-ui app was holding 28× more memory. A web page keeps DOM nodes, styles and React bookkeeping for every message. Ours keeps no page at all; unchanged messages are shared instead of copied, and an old version is freed the moment it’s replaced. Your users can leave long chats open next to everything else without the app becoming what slows their machine down.

Over a minute of streaming, assistant-ui kept more than a full CPU core busy the whole time. Ours did the same job with 4× less CPU time. That is the difference between a laptop that spins up its fans and drains its battery during every long answer, and one that stays cool and quiet.

The four design decisions behind it.

There’s no special benchmark mode here, just four engineering choices. Each one is covered by tests, and the performance record explains how we measured it and which alternatives we tried and rejected.

A simple chat UI re-checks every message whenever a new word arrives. Ours keeps a short list of which rows changed (just their positions, covering the last 64 changes), and each view remembers how far it has read. On each new token only those rows are updated. If you switch branches or edit history, the view rebuilds once, so it always stays correct; that one change is simply slower.

We never let the stream monopolize the loop: we fold bytes in small batches (at most 64 slices), then yield — heartbeats count too. And we coalesce: many chunks arriving together become one update, not one per chunk. The UI always gets a chance to paint between batches.

Turning **bold** and tables into pixels is expensive. We split a message once into settled blocks plus a live tail: each settled block is formatted once and cached forever, and only the last few paragraphs get re-formatted as they stream. On native builds the formatting runs on a worker pool, so the UI thread stays free. In the browser it runs inline — but the same "format once, cache forever" rule keeps cost flat.

We don't keep a web page inside the app. Slint draws the thread itself — as a native window on desktop, or on a canvas in the browser via WebAssembly. No DOM nodes to keep alive, no JavaScript engine in the native case, no framework re-flowing the whole tree on every update. The core has no I/O or UI dependencies, so the same code compiles for wasm32 unchanged — and the WebAssembly demo you can try below is a 2.83 MiB download gzipped.

The full list of changes, with the rejected approaches and their measurements, is in the performance record.

Same protocols as assistant-ui. Keep your backend.

Point it at the endpoint you already have. Messages, streams and tool calls use the same formats, so there is nothing to migrate on the server.

  • Same message formatMessages, branches and tool calls follow assistant-ui’s JSON, so the data your server already produces fits as it is.
  • Same streaming formatsReads assistant-transport, the AI SDK UI message stream and the legacy data stream. If your backend streams to assistant-ui today, it can stream to this.
  • Runs where your app runsThe core has no I/O or UI dependencies, so the same Rust code builds for the desktop and for WebAssembly in the browser.
